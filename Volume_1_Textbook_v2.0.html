3. Beginner-Friendly Introduction: Why Do Containers and Kubernetes Exist?

In the early days of computing, applications ran directly on bare-metal servers. A server running an operating system like Linux or Windows ran all binaries together. If an application leaked memory or monopolized the CPU, every other process on that host starved. Furthermore, dependency conflicts—such as Application A requiring Python 3.8 and Application B requiring Python 3.12—made server management brittle.

Virtual Machines (VMs) solved isolation by placing a hypervisor (e.g., KVM, VMware) on the hardware and running entire independent guest operating systems. However, VMs carry massive overhead: every VM requires gigabytes of disk storage for its guest kernel, takes minutes to boot, and wastes gigabytes of RAM running duplicate operating system services.

Containers offer an elegant, lightweight alternative: Process-level virtualization. Containers do not run a guest kernel; they run as isolated processes directly on the host Linux kernel, sharing its CPU and memory while maintaining strict namespace boundaries.

However, running hundreds of standalone containers across dozens of physical servers creates new operational challenges:

  • What happens when a container crashes at 3:00 AM?
  • How do containers discover and communicate with each other across different servers?
  • How do we roll out new application versions without dropping customer traffic?
  • Which server has enough CPU and memory to host a new container?

Kubernetes is the open-source container orchestration system that automates deployment, scaling, healing, and management of containerized workloads.

4. Detailed Conceptual Explanation & Internal Architecture

At the kernel level, a container is not an actual physical object; it is a standard Linux process isolated by two fundamental kernel subsystems:

  1. Linux Namespaces (Isolation): Restricts what a process can see.
    • pid: Process IDs (a containerized process believes it is PID 1).
    • net: Network interfaces, IP addresses, routing tables, and firewall rules.
    • mnt: Filesystem mount points (isolates root / via pivot_root).
    • ipc: System V IPC and POSIX message queues.
    • uts: Hostname and NIS domain name.
    • user: Maps container root (UID 0) to an unprivileged user on the host.
  2. Control Groups / Cgroups (Resource Metering): Restricts how much a process can use.
    • Limits maximum CPU shares, CFS bandwidth quotas, memory caps, and disk I/O throughput.

Kubernetes abstracts these low-level Linux primitives into resilient, high-level API objects.

CHAPTER 2: CONTAINER ARCHITECTURE AND OCI STANDARDS

1. The Open Container Initiative (OCI)

To avoid vendor lock-in, the industry established the Open Container Initiative (OCI), which governs two core standards:

  1. OCI Image Specification: Defines the layout and format of container images (tarballs containing root filesystems and JSON manifest descriptors).
  2. OCI Runtime Specification: Defines how to unpack and execute an OCI image as a set of Linux namespaces and cgroups (implemented by low-level runtimes like runc and crun).

2. The Container Runtime Interface (CRI)

In early Kubernetes releases, the kubelet directly integrated with Docker via a hardcoded internal bridge called dockershim. In Kubernetes v1.24+, dockershim was completely removed. Modern Kubernetes communicates with container runtimes strictly through the Container Runtime Interface (CRI), a gRPC API.

┌─────────┐      CRI gRPC       ┌──────────────┐     OCI Runtime      ┌──────┐
│ kubelet │ ──────────────────> │  containerd  │ ───────────────────> │ runc │
└─────────┘  /run/containerd/   └──────────────┘   forks container    └──────┘
             containerd.sock           │
                                       ▼
                              ┌──────────────────┐
                              │ containerd-shim  │ ──> [Container Process]
                              └──────────────────┘

1. Control Plane vs. Worker Nodes

  2. Worker Nodes: The compute workhorses. They host the application containers, provide network routing, and execute health checks.

CHAPTER 4: CONTROL PLANE AND WORKER NODE COMPONENTS DEEP DIVE

1. kube-apiserver

The central REST API gateway. Every administrative command from kubectl, every scheduling binding from kube-scheduler, and every heartbeat from kubelet connects to kube-apiserver.

  • State Statelessness: The API server stores no state locally; all data is persisted in etcd.
  • Security Gate: Enforces Authentication, Authorization (RBAC), and Admission Control.

2. etcd

A distributed, consistent key-value store implementing the Raft consensus algorithm. It is the single source of truth for the entire cluster.

  • Ports: Port 2379 (Client requests from apiserver); Port 2380 (Peer communication among etcd members).
  • Quorum Rule: Requires $\lfloor N/2 \rfloor + 1$ members to commit writes.

3. kube-scheduler

Watches for newly created Pods that have no nodeName assigned. It evaluates filtering predicates (hard constraints) and scoring priorities (soft preferences) to select the optimal worker node.

4. kube-controller-manager (KCM)

A single binary compiling multiple control loops (Replication Controller, Node Controller, Endpoints Controller, ServiceAccount Controller). Each loop continuously drives actual cluster state toward the desired state.

5. kubelet (Worker Node Agent)

Runs as a native systemd daemon on every node (not inside a container).

  • Interprets PodSpec objects and calls CRI to create/destroy containers.
  • Mounts storage volumes and configures network namespaces.
  • Continuously executes liveness, readiness, and startup probes.
  • Posts node health heartbeats (Leases) back to the API server.

6. kube-proxy (Network Director)

Runs on every node (typically as a DaemonSet). Watches Services and EndpointSlices, configuring host iptables or IPVS rules to load-balance traffic directed at Service virtual IPs across healthy backend Pods.

PRACTICE EXERCISES & KNOWLEDGE CHECK (CHAPTERS 1–4)

Part A: Knowledge Check Questions

  1. Why was dockershim removed from Kubernetes, and what interface replaced it?
  2. Which control plane component communicates directly with etcd?
  3. What is the minimum number of nodes required to survive 2 simultaneous node failures in an etcd cluster?
  4. Explain the difference between Linux namespaces and cgroups.

Part B: Solutions

  1. dockershim was removed to decouple Kubernetes from proprietary Docker code; it was replaced by the standardized Container Runtime Interface (CRI).
  2. Only kube-apiserver communicates with etcd.
  3. An etcd cluster requires 5 nodes to tolerate 2 node failures ($5/2 + 1 = 3$ quorum required).
  4. Namespaces isolate visibility (what a process sees); cgroups meter and throttle resource consumption (how much CPU/RAM it can use).

  • Understand why kubelet runs as a systemd service while other components run as static pods.

CHAPTER 5: KUBERNETES API SERVER AND API OBJECTS

1. Learning Objectives

2. API Groups and Versioning Architecture

The Kubernetes API is organized hierarchically into:

  1. Core Group (Legacy): Located at /api/v1. Houses original primitives: Pod, Service, Namespace, ConfigMap, Secret, Node, PersistentVolume.
  2. Named Groups: Located at /apis/<group>/<version>. Examples:
    • apps/v1: Deployments, ReplicaSets, StatefulSets, DaemonSets.
    • batch/v1: Jobs, CronJobs.
    • networking.k8s.io/v1: Ingress, NetworkPolicy.
    • storage.k8s.io/v1: StorageClass, VolumeAttachment.
    • rbac.authorization.k8s.io/v1: Role, ClusterRole, RoleBinding.
    • gateway.networking.k8s.io/v1: Gateway, HTTPRoute.

3. API Version Lifecycles

  • v1alpha1: Experimental; subject to breaking changes or removal without notice.
  • v1beta1: Well-tested; enabled by default; deprecated prior to GA.
  • v1 (GA / Stable): Fully supported across minor versions with strict backward compatibility.

CHAPTER 8: LINUX AND NETWORKING FOUNDATIONS FOR KUBERNETES

1. The Fundamental Kubernetes Network Model

Kubernetes imposes four non-negotiable networking requirements:

  1. Every Pod gets its own unique IP address.
  2. Pods on any node can communicate with all pods on any other node without NAT.
  3. Agents on a node (kubelet) can communicate with all pods on that same node.
  4. Pods in the host network of a node can communicate with all pods on all nodes without NAT.

2. Virtual Ethernet Pairs (veth) and Network Namespaces

When a Pod is scheduled:

  1. The container runtime creates an isolated Linux network namespace (netns).
  2. A virtual ethernet pair (veth pair) is created in the kernel. One end (eth0) is moved into the Pod's network namespace, and the peer end (vethXXXX) is plugged into the node's local bridge (e.g., cbr0).
  3. An IP address is allocated from the node's podCIDR allocation by the CNI IPAM plugin.

│     POD NETWORK NAMESPACE       │
│  eth0 (10.244.1.5/24)           │
└───────────────▲─────────────────┘

         veth pair tunnel
                │
┌───────────────▼─────────────────┐

PRACTICE EXERCISES & CKA CHALLENGE (CHAPTERS 5–8)

Challenge: Multi-Container Pod with Declarative YAML

Task: Create a Pod named log-processor in namespace observability:

  1. Main container app running busybox:1.36 writing timestamped logs every 5 seconds to /var/log/app.log.
  2. Sidecar container logger running busybox:1.36 reading and streaming /var/log/app.log to standard output.
  3. Both containers share a volume named shared-logs of type emptyDir.

Solution Manifest:

apiVersion: v1
kind: Namespace
metadata:
  name: observability
---
apiVersion: v1
kind: Pod
metadata:
  name: log-processor
  namespace: observability
spec:
  volumes:
  - name: shared-logs
    emptyDir: {}
  containers:
  - name: app
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args:
    - >
      while true; do
        echo "$(date) - Application event processing" >> /var/log/app.log;
        sleep 5;
      done
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log
  - name: logger
    image: busybox:1.36
    command: ["/bin/sh", "-c"]
    args: ["tail -n+1 -f /var/log/app.log"]
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log

Verification:

kubectl apply -f solution.yaml
kubectl logs -n observability log-processor -c logger

Expected output: Continuous stream of timestamped log entries originating from the app container.

2. Linux Operating System Prerequisites

Every Kubernetes node (control plane or worker) requires kernel module configuration and sysctl networking parameters:

# 1. Disable Linux Swap (Mandatory for Kubelet memory management)
sudo swapoff -a
sudo sed -i '/swap/d' /etc/fstab

# 2. Forwarding IPv4 and letting iptables see bridged traffic
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF

sudo modprobe overlay
sudo modprobe br_netfilter

# 3. Sysctl parameters required by CNI
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF

sudo sysctl --system

sudo systemctl enable containerd

CHAPTER 17 & 18: CLUSTER UPGRADES & SAFE NODE MAINTENANCE

1. Zero-Downtime Node Maintenance Algorithm

When patching an OS kernel or upgrading node components, follow the three-step lifecycle:

  1. Cordon: Prevents new workloads from being scheduled on the node.
    kubectl cordon worker-01
  2. Drain: Safely evicts existing Pods using the Eviction API, respecting PodDisruptionBudgets.
    kubectl drain worker-01 --ignore-daemonsets --delete-emptydir-data --force
  3. Perform Maintenance & Uncordon:
    # Upgrade node packages, reboot if necessary, then restore scheduling
kubectl uncordon worker-01

2. Kubeadm Minor Version Upgrade Sequence

Always upgrade the Control Plane before Worker Nodes. Never skip minor versions (e.g., upgrade v1.30 -> v1.31 -> v1.32 sequentially):

# --- ON CONTROL PLANE NODE ---
# 1. Upgrade kubeadm
sudo apt-mark unhold kubeadm
sudo apt-get update && sudo apt-get install -y kubeadm=1.31.2-1.1
sudo apt-mark hold kubeadm

# 2. Check upgrade plan
sudo kubeadm upgrade plan

# 3. Apply cluster upgrade
sudo kubeadm upgrade apply v1.31.2 -y

# 4. Drain node & upgrade kubelet/kubectl
kubectl drain controlplane --ignore-daemonsets
sudo apt-mark unhold kubelet kubectl
sudo apt-get install -y kubelet=1.31.2-1.1 kubectl=1.31.2-1.1
sudo apt-mark hold kubelet kubectl

sudo systemctl daemon-reload
sudo systemctl restart kubelet
kubectl uncordon controlplane

# --- ON WORKER NODES ---
kubectl drain worker-01 --ignore-daemonsets --delete-emptydir-data
ssh worker-01
sudo apt-mark unhold kubeadm
sudo apt-get update && sudo apt-get install -y kubeadm=1.31.2-1.1
sudo apt-mark hold kubeadm
sudo kubeadm upgrade node
sudo apt-mark unhold kubelet kubectl
sudo apt-get install -y kubelet=1.31.2-1.1 kubectl=1.31.2-1.1
sudo apt-mark hold kubelet kubectl
sudo systemctl daemon-reload
sudo systemctl restart kubelet
exit
kubectl uncordon worker-01

CHAPTER 16: SERVICEACCOUNTS AND POD AUTHENTICATION

1. ServiceAccount Token Projection

Modern Kubernetes (v1.24+) does not automatically create static bearer token secrets for ServiceAccounts. Instead, tokens are projected dynamically into pods as projected volumes using the TokenRequest API:

  • Tokens have an expiration time (default 1 hour).
  • Tokens are automatically rotated by kubelet without restarting the container.
  • Bound directly to the Pod's lifecycle.
apiVersion: v1

  name: app-reader-sa
  namespace: default
---
apiVersion: v1
kind: Pod
metadata:
  name: app-reader-pod
spec:
  serviceAccountName: app-reader-sa
  containers:

    image: curlimages/curl:8.10.1

CHAPTER 20: HIGHLY AVAILABLE KUBERNETES CLUSTERS

1. Stacked vs. External etcd Topologies

  1. Stacked etcd Topology: etcd runs as static pods on the same nodes as the control plane components. Simpler to manage via kubeadm init --upload-certs. Requires at least 3 control plane nodes.
  2. External etcd Topology: etcd runs on dedicated external servers. Decouples control plane compute from etcd storage I/O.

2. Control Plane Load Balancer

A high-availability control plane requires a TCP load balancer (e.g., HAProxy + Keepalived) in front of the API servers:

  • Virtual IP: 192.168.1.100:6443
  • Backends: cp-node-1:6443, cp-node-2:6443, cp-node-3:6443
  • Pass --control-plane-endpoint="192.168.1.100:6443" to kubeadm init.

CHAPTER 21: ETCD ARCHITECTURE, BACKUP AND DISASTER RECOVERY

1. The Definitive 7-Step etcd Disaster Recovery Runbook

This is the single most heavily tested administrative procedure on the CKA examination.

# STEP 1: Identify etcd Static Pod Configuration & PKI Paths
sudo grep -E "cert-file|key-file|trusted-ca-file|data-dir" /etc/kubernetes/manifests/etcd.yaml

# STEP 2: Save Snapshot using etcdctl v3
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/snapshot-pre-disaster.db

# STEP 3: Verify Snapshot Integrity
ETCDCTL_API=3 etcdctl --write-out=table snapshot status /opt/snapshot-pre-disaster.db

# STEP 4: Stop kube-apiserver by moving manifest temporarily
sudo mv /etc/kubernetes/manifests/kube-apiserver.yaml /tmp/

# STEP 5: Restore Snapshot to a BRAND NEW Target Data Directory
ETCDCTL_API=3 etcdctl snapshot restore /opt/snapshot-pre-disaster.db \
  --data-dir=/var/lib/etcd-from-backup \
  --initial-cluster="master=https://127.0.0.1:2380" \
  --initial-cluster-token="etcd-cluster-token" \
  --initial-advertise-peer-urls="https://127.0.0.1:2380" \
  --name="master"

CHAPTER 24 & 25: PODS, POD LIFECYCLE & MULTI-CONTAINER PATTERNS

1. Pod Phase Transitions

A Pod's lifecycle is tracked via status.phase:

  • Pending: Pod accepted by the API server, but one or more containers are not yet created (often awaiting scheduling or image download).
  • Running: Pod bound to a node, all containers created, and at least one container is running or starting.
  • Succeeded: All containers terminated successfully (exit code 0); cannot restart.
  • Failed: All containers terminated, with at least one container terminating in failure (non-zero exit code).
  • Unknown: State cannot be obtained (typically due to network loss between kubelet and API server).

2. Multi-Container Pod Design Patterns

  1. Sidecar Pattern: Enhances or extends the main container (e.g., streaming logs from an emptyDir volume to centralized Elasticsearch or Prometheus metrics exporter).
  2. Ambassador Pattern: Proxies network traffic from the local pod to the outside world (e.g., connecting to localhost:6379 while the ambassador routes to a sharded Redis cluster).
  3. Adapter Pattern: Standardizes output across disparate application formats (e.g., transforming legacy application metric formats into Prometheus exposition format).
  4. Init Containers: Sequential initialization containers that run to complete exit 0 before application containers start.

CHAPTER 26: DEPLOYMENTS AND REPLICASETS

1. Deployment Strategies: Recreate vs. RollingUpdate

  • Recreate Strategy: Terminates all existing pods before creating new pods (spec.strategy.type: Recreate). Results in downtime but prevents two application versions from executing concurrently.
  • RollingUpdate Strategy: Gradually replaces old pods with new pods. Governed by:
    • maxSurge: Max pods created above desired count (default 25%).
    • maxUnavailable: Max pods unavailable during update (default 25%).

CHAPTER 30: RESOURCE REQUESTS, LIMITS & KERNEL CFS QUOTAS

1. Compute Units in Kubernetes

  • CPU: Specified in millicores ($1000\text{m} = 1\text{ vCPU / core}$). It is a compressible resource: exceeding limits results in CPU cycle throttling via Linux CFS, not termination.
  • Memory: Specified in bytes with binary SI suffixes (128Mi, 1Gi). It is an incompressible resource: exceeding limits results in an instant kernel OOMKilled (Exit Code 137).

2. Quality of Service (QoS) Classes

Kubernetes assigns each Pod a QoS class based on its request/limit declarations:

  1. Guaranteed (Highest Priority): Every container specifies CPU and Memory requests and limits, and requests strictly equal limits. Safest against eviction.
  2. Burstable (Medium Priority): At least one container specifies requests or limits, and requests are less than limits.
  3. BestEffort (Lowest Priority): No container specifies any requests or limits. These pods are killed first when node memory pressure occurs.

CHAPTER 32–35: ADVANCED SCHEDULING MECHANISMS

1. NodeSelector vs. NodeAffinity

  • nodeSelector: Simple key-value label equality (disk: ssd).
  • nodeAffinity: Expressive rule syntax using operators (In, NotIn, Exists, DoesNotExist, Gt, Lt):
    • requiredDuringSchedulingIgnoredDuringExecution: Hard filtering predicate.
    • preferredDuringSchedulingIgnoredDuringExecution: Soft scoring priority.
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: topology.kubernetes.io/zone
            operator: In
            values: ["us-east-1a", "us-east-1b"]
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: instance-type
            operator: In
            values: ["compute-optimized"]

2. Taints and Tolerations

  • Taints repel pods from nodes:
    kubectl taint nodes worker-01 dedicated=special:NoSchedule
    Taint Effects:
    • NoSchedule: New pods without matching toleration are not placed on the node. Existing pods remain.
    • PreferNoSchedule: Soft preference; scheduler tries to avoid placing pods without toleration.
    • NoExecute: Pods without matching toleration are immediately evicted from the node.
  • Tolerations allow pods to be scheduled on tainted nodes:
    spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "special"
    effect: "NoSchedule"

3. Pod Affinity and Anti-Affinity

Co-locates or isolates pods relative to other pods within a topological domain:

spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values: ["web-frontend"]
        topologyKey: "kubernetes.io/hostname"

Effect: Guarantees that two web-frontend replicas will never be scheduled on the same physical host.

CHAPTER 39–41: KUBERNETES NETWORKING & CNI ARCHITECTURE

1. Container Network Interface (CNI)

CNI is a standard specification defining plugins to configure network interfaces when containers are started and destroyed.

  • Located at: /opt/cni/bin/ (Executables: bridge, loopback, host-local, calico, flannel).
  • Network configurations located at: /etc/cni/net.d/ (Evaluated alphabetically in lexicographical order).

2. Pod-to-Pod Communication Across Nodes

  1. Pod A (10.244.1.5) sends a packet to Pod B (10.244.2.10).
  2. The packet traverses veth0 into the host Linux bridge (cbr0).
  3. The host routing table directs packets destined for 10.244.2.0/24 to the CNI overlay device (e.g., flannel.1 or calico-tun).
  4. The overlay interface encapsulates the inner IP packet inside an outer UDP packet (Port 4789/8472 VXLAN) addressed to Worker Node 2 (192.168.1.20).
  5. Worker Node 2 decapsulates the UDP packet and delivers the original IP packet to Pod B via its local bridge.

CHAPTER 42 & 43: KUBERNETES SERVICE TYPES & PACKET NAT

1. Service Types Compared

  • ClusterIP (Default): Allocates a virtual cluster-internal IP reachable only from within the cluster.
  • NodePort: Allocates a high-range static port (30000–32767) on every node in the cluster. Traffic sent to <NodeIP>:<NodePort> is forwarded to the Service.
  • LoadBalancer: Automatically provisions a cloud load balancer (e.g., AWS NLB, GCP Network Load Balancer) that routes to the NodePort.
  • ExternalName: Maps the Service to a DNS CNAME record (e.g., my-db.external-service.com) without proxying.

2. Service YAML Definition

    targetPort: 8080 # Port listening on the container

CHAPTER 47: GATEWAY API DEEP DIVE

1. Why Gateway API Replaces Ingress

Ingress suffered from monolithic configuration where cluster administrators and application teams collided in a single resource. Gateway API decouples routing into distinct roles:

  1. Infrastructure Provider: Defines GatewayClass.
  2. Cluster Operator: Deploys Gateway (declares IP addresses, ports, and TLS certs).
  3. Application Developer: Attaches HTTPRoute or GRPCRoute (defines paths, weights, and header rewrites).

2. Complete Gateway API Architecture & Manifests

Step 1: Gateway Resource (Cluster Operator)

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: prod-gateway
  namespace: gateway-infra
spec:
  gatewayClassName: standard-gateway
  listeners:
  - name: http-listener
    protocol: HTTP
    port: 80
    allowedRoutes:
      namespaces:
        from: All

Step 2: Advanced HTTPRoute with Canary Traffic Splitting (Developer)

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: checkout-route
  namespace: store
spec:
  parentRefs:
  - name: prod-gateway
    namespace: gateway-infra
  hostnames:
  - "checkout.example.com"
  rules:
  # Rule 1: Header-based routing for beta testers
  - matches:
    - headers:
      - name: X-Beta-Tester
        value: "true"
    backendRefs:
    - name: checkout-v2-canary
      port: 8080
  # Rule 2: 90/10 Canary traffic split for regular users
  - matches:
    - path:
        type: PathPrefix
        value: /checkout
    backendRefs:
    - name: checkout-v1-stable
      port: 8080
      weight: 90
    - name: checkout-v2-canary
      port: 8080
      weight: 10

CHAPTER 48: NETWORKPOLICIES

1. The Default-Deny Security Model

By default, all pods in Kubernetes can receive and send traffic without restriction. Applying a NetworkPolicy isolates matching pods, switching them to default-deny.

Default-Deny All Ingress Traffic:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: secure-zone
spec:
  podSelector: {}
  policyTypes:
  - Ingress

Fine-Grained 3-Tier NetworkPolicy: Allow ingress to db pods on port 5432 only from backend pods in namespace api:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-backend-to-db
  namespace: data
spec:
  podSelector:
    matchLabels:
      role: database
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          environment: production
      podSelector:
        matchLabels:
          app: backend
    ports:
    - protocol: TCP
      port: 5432

CRITICAL SYNTAX NOTE: In the from list, separating namespaceSelector and podSelector with a hyphen (-) creates an OR relationship. Omitting the hyphen between them creates an AND relationship!

3. Storage Access Modes

  • ReadWriteOnce (RWO): Volume can be mounted as read-write by a single node. Multiple pods on that same node can read and write concurrently.
  • ReadOnlyMany (ROX): Volume can be mounted read-only by many nodes simultaneously.
  • ReadWriteMany (RWX): Volume can be mounted read-write by many nodes simultaneously (requires distributed filesystems like NFS, CephFS, or GlusterFS).
  • ReadWriteOncePod (RWOP): GA in modern Kubernetes. Restricts volume access to a single pod in the entire cluster. Essential for databases preventing multi-pod write corruption.

4. Reclaim Policies

  • Retain: When the PVC is deleted, the PV remains intact in Released status. Data is preserved for manual recovery.
  • Delete: When the PVC is deleted, the underlying cloud storage asset is automatically destroyed.

CHAPTER 58: CONTAINER STORAGE INTERFACE (CSI)

CHAPTER 61 & 62: POD AND DEPLOYMENT TROUBLESHOOTING

Diagnostic Decision Matrix:

  1. CrashLoopBackOff:
    • Step 1: kubectl logs <pod-name> --previous
    • Step 2: kubectl describe pod <pod-name> (Check Exit Code: 137 = OOMKilled; 0 = Batch process exited; 1 = App error).
  2. ImagePullBackOff:
    • Check image spelling, tag existence, and imagePullSecrets.
  3. CreateContainerConfigError:
    • Referenced ConfigMap or Secret does not exist in the pod's namespace.
  4. Deployment Replicas Not Updating:
    • Run kubectl rollout status deployment/<name>.
    • Check for resource quota violations or failing readiness probes holding back rolling updates.

CHAPTER 67 & 68: API SERVER & ETCD OUTAGE RECOVERY

1. Recovering a Crashed kube-apiserver

When kubectl commands return The connection to the server 192.168.1.10:6443 was refused:

  1. SSH into the control plane host.
  2. The API server runs as a static pod. Inspect /etc/kubernetes/manifests/kube-apiserver.yaml.
  3. Check runtime container status:
    sudo crictl ps -a --name kube-apiserver
sudo crictl logs $(sudo crictl ps -a --name kube-apiserver -q | head -n 1)
  4. Common failure causes:
    • Typo in flag arguments inside /etc/kubernetes/manifests/kube-apiserver.yaml.
    • Expired certificates in /etc/kubernetes/pki/.
    • etcd static container is down or unresponsive on port 2379.

2. Restoring etcd from Corrupted State

Execute the proven disaster recovery workflow:

ETCDCTL_API=3 etcdctl snapshot restore /opt/backup.db \
  --data-dir=/var/lib/etcd-recovered \
  --initial-cluster="controlplane=https://127.0.0.1:2380" \
  --initial-cluster-token="k8s-cluster" \
  --initial-advertise-peer-urls="https://127.0.0.1:2380" \
  --name="controlplane"

sudo sed -i 's|path: /var/lib/etcd|path: /var/lib/etcd-recovered|g' /etc/kubernetes/manifests/etcd.yaml

CHAPTER 69 & 70: NETWORKING, DNS & STORAGE TROUBLESHOOTING

1. CoreDNS Failure Drill

  • Symptom: Application pods throw Name or service not known.
  • Root Cause 1: CoreDNS pods stuck in CrashLoopBackOff with Loop ... detected. Occurs when host /etc/resolv.conf loops back to 127.0.0.53. Update host DNS to external IP (e.g. 8.8.8.8) and restart CoreDNS.
  • Root Cause 2: NetworkPolicy in application namespace lacks egress rule on UDP port 53.

2. Service Endpoints Missing

  • Symptom: curl http://<service-ip> hangs or drops connection.
  • Diagnostic: kubectl get endpoints <service-name>. If <none>, the service label selector does not match the pod labels or the pods are failing readiness probes.

CHAPTER 71 & 72: INTEGRATED MULTI-COMPONENT FAILURE DRILLS

Master Integrated Drill: The "Blackout" Control Plane

Scenario: A cluster operator accidentally ran a cleanup script on the control plane node. The cluster is completely down:

  • kubectl returns connection refused.
  • kubelet is inactive.
  • etcd data directory was wiped.

Step-by-Step Resolution Runbook:

  1. Restart Kubelet Daemon:
    sudo systemctl daemon-reload
sudo systemctl restart kubelet
sudo systemctl status kubelet
  2. Verify Static Pod Manifest Directory: Inspect /var/lib/kubelet/config.yaml and confirm:
    staticPodPath: /etc/kubernetes/manifests
  3. Restore etcd Database from Latest Snapshot:
    ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot.db \
  --data-dir=/var/lib/etcd-restored \
  --initial-cluster="master=https://127.0.0.1:2380" \
  --name="master"
  4. Point etcd Manifest to Restored Data: Update hostPath in /etc/kubernetes/manifests/etcd.yaml to /var/lib/etcd-restored.
  5. Verify kube-apiserver Comes Online: Wait 30 seconds for kubelet to launch static containers. Verify with:
    sudo crictl ps | grep kube-apiserver
kubectl get nodes
  6. Uncordon Nodes & Verify Workload Healing:
    kubectl get pods -A

CHAPTER 77: THE TOP 10 DEADLIEST CANDIDATE MISTAKES

  1. Forgetting to Switch Context: Every task begins with a context switch command:
    kubectl config use-context <context-name>
    Failing to run this executes the solution on the wrong cluster, awarding zero points.
  2. Working in the Wrong Namespace: Always append -n <target-namespace> or verify current namespace.
  3. Using Deprecated Flags: Running kubectl ... --record or using obsolete batch/v1beta1 APIs.
  4. Writing YAML from Scratch: Always use kubectl run ... $do or copy from official docs.
  5. Overwriting the etcd Data Directory: Restoring etcd directly into /var/lib/etcd without specifying a new target directory.
  6. Forgetting to Uncordon Nodes: Leaving upgraded nodes cordoned.
  7. Indentation Errors in YAML: Mixing tabs and spaces in vim. Configure ~/.vimrc first!
  8. Ignoring Pod Readiness: Assuming a pod is working because phase is Running, without verifying readiness probes.
  9. Failing to Verify Cluster Status: Not testing kubectl get nodes or curl endpoints before moving to the next task.
  10. Panic and Time Freezing: Spending 25 minutes stuck on a 4% task instead of flagging it.
